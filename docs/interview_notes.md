# Interview notes

Short answers, with the file that backs each one.

- **Why do the numbers look worse than the first version of this project?** The first version reported 100% precision and 94.2% recall on easy synthetic data whose noise and matching rules were written by the same person, and the rules were refined after seeing results. The hard dev and held-out sets add shared family phones, recycled numbers, common names, nickname variants and records where both phone and email changed. The held-out figures are the honest ones (README, Key Results).
- **How do you stop yourself tuning on the test data?** Thresholds and rules are chosen on `data/dev` only. A frozen configuration is hashed and evaluated once on `data/heldout`; the hash and git commit go to `outputs/heldout_ledger.json`, and `load_dataset("heldout")` refuses other callers. See `data/README.md`.
- **How was precision calculated?** Pair level, TP / (TP + FP), against an answer key that only evaluation code reads (`tests/test_no_leakage.py`). Cluster-level B-cubed and purity sit beside it because pair recall over-weights 3-record customers (3 pairs vs 1).
- **Which matcher is best and why?** Fellegi-Sunter, chosen on dev. It beats the fuzzy rules mostly on recall because it combines weak evidence (similar name, same pincode, same signup date) instead of requiring one rule to fire. The comparison table and analysis are in `docs/methodology.md` and `outputs/matcher_comparison.csv`.
- **What did the matcher get wrong?** `docs/case_studies.md`: a missed duplicate with a blank name, a false merge from one digit off with reversed names, and a survivorship surprise.
- **What happens at scale?** `outputs/scale_benchmark.csv`: the standard matcher hits a `MemoryError` at 500k records under the benchmark's 6 GB cap, and the scalable matcher's EM breaks down there (precision about 1%). Freezing the weights fitted on an extract gives 43.9% precision, because the prior odds of a candidate pair fall as 1/N. Raising the thresholds by log2(N / 50k) gives 92.6% precision at 61.8% recall. That correction came from the argument, not from tuning on the benchmark, and it is one run on one dataset.
- **Why a review queue?** Blank-name candidates are never auto-merged ("blank is better than wrong"), yet 79% of the dev blank-name pairs that share an identical phone and email are real duplicates. Ranking them by expected value and reviewing 500 pairs lifts simulated recall from 72.8% to 91.1% (perfect reviewer, labelled as a simulation).
- **Why did the business estimate come out negative?** The unit costs in `config/assumptions.json` are placeholders and a wrong merge is priced at INR 200 against INR 0.25 per message. The estimate shows which assumptions flip the sign (`docs/business_impact.md`); it is not a forecast.
- **What improved raw to standardized?** On the easy dataset the all-rules pass rate went 7.7% to 73.9% from repairing formatting; merging added 2.8 pp more on a different denominator (see the like-for-like figure in `outputs/metrics.json`).
- **Main weakness left?** All data except Febrl is synthetic from one generator. Held-out measures a new sample, not a new noise model.
