# Methodology

1. **Standardize** six fields; unfixable values become NULL (never guessed).
2. **Candidates**: pairs sharing an exact phone, email, or full name + pincode. NULLs never match.
3. **Decision**: accept when names agree (same surname and first name, or an initial); when a name is missing accept only if phone AND email both agree; otherwise reject. Relatives sharing a phone are therefore kept apart.
4. **Clusters**: connected components of accepted pairs.
5. **Survivorship**: see `data_dictionary.md`.
6. **Evaluation**: positive class = a pair of records that are the same customer. Every within-cluster pair is a predicted pair; every within-entity pair in the answer key is a true pair. Precision = TP/(TP+FP), recall = TP/(TP+FN), F1 = 2PR/(P+R). Record-level counts are reconciled separately (`reconciliation` in `outputs/metrics.json`): rows removed = raw − golden; rows that should be removed = raw − true customers.
7. **Leakage control**: `answer_key.csv` is opened only in `validation.py`; steps 1-4 never read it.
8. **Candidate coverage**: 8 of the 43 missed pairs share no key and cannot be generated by the blocking keys; 35 are generated but rejected because a name is blank (see `outputs/missed_pairs_analysis.csv`).

No fuzzy customer matching is used. Key-sharing was checked on this dataset: no phone or email is shared by more than 3 standardized records, so no frequency cut-off for placeholder identifiers is applied; real data would need one.

## Matchers compared (added in the upgrade)

Three matchers share one interface (`src/customer_master/matchers/`) and the same blocking:

1. **exact-key**: the original rules (exact phone, email or name + pincode, name guard).
2. **fuzzy-rules**: Jaro-Winkler / Levenshtein name similarity and an Indian-name phonetic key, used for blocking and scoring.
3. **fellegi-sunter**: m/u probabilities estimated by EM, a match weight per pair, and three decisions: auto-merge, review, non-match.

Blocking keys (phone, email, phonetic name + pincode, among others) replace the all-pairs self-join. The configuration is chosen on `data/dev` only, frozen, and evaluated once on `data/heldout`. Results: `outputs/matcher_comparison.csv`, with 20-seed intervals in `outputs/multiseed_summary.csv`. On held-out, fuzzy rules beat exact keys on recall (57.0% vs 46.9%) and slightly on precision (96.8% vs 95.4%). Fellegi-Sunter reaches 74.0% recall at 96.5% precision by combining weak evidence instead of requiring one rule to fire, at about 10x the runtime of fuzzy rules (2.0 s vs 0.2 s on 5k records). Figures: `outputs/matcher_comparison.csv`.
